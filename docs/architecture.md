# Архитектура системы

Проект построен на микросервисной архитектуре (или сильно сегментированном монолите), где основные тяжелые задачи вынесены в отдельные воркеры и общаются через очереди сообщений.

## Основные компоненты

### 1. Bot Polling (`src.bot.main`)
Основной процесс, который взаимодействует с Telegram API через библиотеку `aiogram`.
- Принимает сообщения от пользователей.
- Управляет состояниями (FSM) в Redis.
- Выполняет легкие операции с базой данных.
- Отправляет тяжелые задачи (например, запросы к AI) в RabbitMQ.

### 2. AI Worker (`src.workers.ai_worker`)
Обрабатывает запросы к языковым моделям (LLM).
- Слушает очередь задач из RabbitMQ.
- Взаимодействует с OpenAI API или Groq.
- Возвращает готовые ответы в очередь для отправки пользователю.

### 3. Sender Worker (`src.workers.sender_worker`)
Специализированный воркер для отправки сообщений.
- Позволяет избежать блокировок основного потока бота.
- Гарантирует доставку уведомлений и массовых рассылок.
- Работает с очередью `q_notifications`.

### 4. Scheduler (`src.workers.scheduler`)
Планировщик периодических задач (APScheduler).
- Ежедневный подбор пар для дейтинга (`run_daily_matching`).
- Рассылка напоминаний и ежедневных активностей.
- Обновление конфигураций из внешних источников.

## Схема взаимодействия данных
1. **User** -> **Telegram** -> **Bot Polling**.
2. **Bot Polling** -> **Redis** (сохранение состояния).
3. **Bot Polling** -> **RabbitMQ** (задача для AI).
4. **AI Worker** -> **OpenAI API** -> **AI Worker**.
5. **AI Worker** -> **RabbitMQ** (готовый ответ).
6. **Sender Worker** -> **Telegram** -> **User**.

## Инфраструктура
- **PostgreSQL**: Основное хранилище (пользователи, анкеты, QR-коды).
- **PgBouncer**: Пул соединений для эффективной работы с БД.
- **Redis**: Кэширование и FSM.
- **RabbitMQ**: Шина данных для асинхронного взаимодействия.
- **Monitoring**: Prometheus (метрики), Loki (логи), Grafana (визуализация).
